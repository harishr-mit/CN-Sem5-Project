# NoBu Shooter — Implementation Decisions & Assumptions

Decisions that are not obvious from the code, one line each with the reason. Originally required by the v1 spec (`docs/archive/SPEC-v1.md` §3); kept for all later phases (`PHASES.md`).

---

### Architectural & Simulation Assumptions

1. **Monorepo Layout**: Built with npm workspaces under `./NoBu-Shooter` (`shared`, `server`, `emulator`, `client`) with root convenience proxies so commands like `npm run demo`, `npm test`, and `npm run smoke` operate smoothly from either root or project directory.
2. **Fixed Timestep & Determinism**: The game simulation strictly runs at 60 Hz (`dt = 1/60`) using integer key masks and normalized diagonal vectors (`Math.SQRT1_2`) without trig in the player movement path to prevent phantom prediction discrepancies.
3. **Transport Semantics**: WebSockets transport JSON messages where each text frame is treated as an independent datagram by the network emulator pipeline, with 28 simulated header bytes added for bandwidth calculation.
4. **Art and Asset Pipeline**: In accordance with the prompt ("do not generate textures and models, leave them as references and add comments to mark the spot"), all game visuals are rendered procedurally via Phaser 3 Graphics with explicit `/* TEXTURE: <name> */` comments marking integration points for future custom sprites.
5. **Bot Execution Model**: Bots are simulated server-side and feed identical input structures into room authority without network latency; their *input* bypasses the emulator, but their *state* reaches each client through it like any remote player. (Phase 5 adds UDP network players whose own traffic is impaired.)
6. **Reconciliation Error Smoothing**: Prediction errors below `epsilonPx` (0.01 px) are ignored; errors between 0.01 px and 64 px are exponentially decayed via `smoothHalfLifeMs` (80 ms); errors exceeding 64 px execute an instantaneous snap.
7. **Event Redundancy**: Server snapshots redundantly retransmit game events from the preceding 500 ms; clients track and deduplicate events by unique `eid`.
8. **Browser Port Alignment**: Client Vite dev server runs on port 5173, Game Server on port 8080, Emulator Data on port 9000, and Emulator Control on port 9001.

### Phase 1 decisions (2026-10-09)

9. **Input sending (redundancy off)**: every input is sent exactly once, in the next 30 Hz message after it is created (2 inputs per message). Sending only the newest input — the v1 behaviour — silently dropped half the inputs and caused corrections on a perfect network.
10. **Reorder delay default 80 ms**: a reordered input packet only acts like loss if it arrives after a newer input was already consumed, which needs a delay above the send interval + one tick (~50 ms). With the v1 default (40 ms) the server's sorted input queue absorbed reordering completely, so the effect could not be demonstrated. Covered by `tests/netcode.test.ts`.
11. **Interpolated alive/dead state**: remote players' alive flag comes from the interpolated snapshot pair (not the latest snapshot), so a remote player doesn't vanish ~100 ms before the projectile that killed them reaches them on screen. Respawns (life change) are never interpolated across the arena.
12. **Input → Screen definition**: prediction on = time from the input sample to the presentation of the next frame (sample → render + one frame). Prediction off = ack delay (input creation → snapshot acknowledging it) + interpolation delay (if on) + one frame. "Ack delay" is shown alongside.
13. **Server loop on Windows**: OS timers fire every ~15.6 ms on Windows (measured for both `setTimeout` and `Atomics.wait`), so the loop sleeps one timer quantum and yields with `setImmediate` only for the final ~1 ms before each tick: ~1 % CPU instead of a fully spun core, tick rate unchanged (60–61 Hz).
14. **Process lifetime**: services run as single node processes (`node --import tsx`, Vite via its JS API) and exit by themselves when the launcher's PID (`NOBU_PARENT_PID`) disappears, because Windows does not kill children with their parent.
15. **Emulator session labels**: each `NetClient` connects with a unique label (`<name>-<4 random chars>`), which the UI uses to pick *its own* session from the emulator stats (loss tiles, packet strip). Session RNGs share the CLI seed, which keeps Compare panes under comparable random conditions.
16. **Presets are complete configs**: applying a preset replaces the whole link config (missing fields take defaults), so no setting leaks from the previous preset (e.g. burst loss after Nightmare).
17. **Lab room**: always `RUNNING` with any number of players (GAMERULES.md §14); no spawn protection because firing is disabled there.
18. **Dev-mode warnings**: React StrictMode mounts the Compare view twice in development, producing harmless "WebSocket is closed before the connection is established" warnings (one per pane client, the spectator and the emulator control client); `NetClient` and `EmulatorClient` ignore callbacks from the discarded connection (generation counter / socket identity), so no duplicate control socket or reconnect loop is left behind. Production builds don't double-mount.

### Phase 2 decisions (2026-10-09, `docs/PHASE2_PLAN.md` D1–D7)

19. **Movers are `PlayerSnap` entries** with a `mover` field, kept outside the room's player map (no player cap, no inputs, ids from the player id counter). Interpolation — and later sync models — treat them like any remote player.
20. **Mover paths are pure functions of server time** (`shared/src/sim/movers.ts`, `position = moverPath(pattern, tick / 60)`), continuous (no teleports), 200 px/s, and clear of obstacles by ≥ 20 px (tested). Any client can compute the exact true position at any server time.
21. **True server time comes from the spectator**: Compare always opens a direct (unimpaired) spectator connection; its clock offset (`serverNow() = now + EMA(st − arrival)`) is the truth clock for every pane. Expected error ±1–2 ms (snapshot send times jitter with the Windows timer and the hybrid server loop; the EMA averages it out).
22. **Remote error = delay, not distance**: for each drawn mover, τ is the delay at which the true path passes through the drawn position *heading the same way* (a back-and-forth path passes each point twice). Lag = median τ, wobble = interquartile range / 1.35 (= std-dev for normal noise, robust to rare glitches such as a buffer underrun), plus mean distance (px) and frozen frames (true position moved > 0.5 px, drawn < 0.1 px) over a 2 s window. Raw distance depends on the path's shape (stops, reversals) and would rate interpolation as worse. Measured at 50 ± 30 ms (browser): interpolation off ≈ 75 ± 26 ms, 60–70 % frozen; on ≈ 160 ± 3 ms, 2 % frozen.
23. **Frozen % depends on the display**: at 60 Hz with 30 Hz snapshots, a pane without interpolation repeats every other frame (≈ 50 %, more under jitter); a 144 Hz monitor would show ≈ 79 %.
24. **One shared input driver**: in Compare, `InputDriver` owns the keyboard and a single fixed 60 Hz loop that gives every pane's client the same keys on the same step and flushes all inputs together at 30 Hz. Panes' Phaser scenes only render. Firing is not driven (the lab room rejects it).
25. **Comparison presets change one setting**; their network conditions are complete emulator configs (named or ad-hoc presets), so nothing carries over. "Prediction off vs on" keeps interpolation on in both panes.
26. **Pane layout**: `layoutPanes` tries every rows × cols grid and keeps the largest canvas; canvases are exactly 16:9, so there's no letterboxing (measured 0–0.2 %); leftover space (or an empty grid cell) holds the dock. The network drawer overlays the panes so opening it never resizes them.
27. **Compare rendering performance**: each pane renders at its displayed size (`Phaser.Scale.RESIZE` + camera zoom) instead of a full 1280×720 frame shrunk by CSS; static art (grid, walls) is baked into textures once; mover bodies, trail dots and truth rings are pooled sprites. Phaser re-tessellates every `Graphics` object each frame, which had made 5 panes CPU-bound at 20 fps on the dev laptop's Intel UHD GPU; now 60 fps with 4 panes + reference at 1920×1080. Quick Match keeps `FIT` (unchanged look).

### Bug-fix run merged from branch `game` (2026-10-09, merged 2026-10-10)

28. **Movement keys are page-level** (`client/src/game/input.ts`): in Quick Match one `window` capture-phase listener tracks keys by `KeyboardEvent.code` (physical position: works on AZERTY etc. and while an IME reports `keyCode` 229) and does not skip events another handler already `preventDefault`-ed. Phaser's keyboard is disabled (`input.keyboard: false`): it `preventDefault`s captured keys and ignores already-prevented events, which hid keys from every other listener. Keys are released on window blur / tab hide. Compare's `InputDriver` (#24) uses the same key mapping and text-field rule. Hotkeys (`Tab`, `1`–`5`, `P`/`R`/`I`/`G`, movement) are ignored only in text fields, not on a focused slider or checkbox. A browser extension that intercepts keys before the page (Vimium: `d`, `r`, `p`, digits) still wins; the README's troubleshooting section says how to exclude the demo.
29. **One lab spawn point**: every `lab` player spawns at `rooms.lab.spawn` (880, 360), so every Compare pane's player starts in the same place (players never collide and the lab has no firing). With identical inputs from the `InputDriver`, the server paths are identical (`tests/netcode.test.ts`), so in the REF pane the panes' players overlap. The point is ≥ 108 px from every mover path and clear of obstacles (`tests/movers.test.ts`); the `game` branch had (640, 520), which lies on the zigzag lane. Under loss without input redundancy each link drops different inputs and the players drift apart (~40 px at 10 % in the harness) — the Redundancy comparison preset.
30. **Leaving a match**: **◄ LEAVE MATCH** (HUD) and the Esc menu's **◄ LEAVE MATCH — BACK TO MAIN MENU** drop both clients (their effect cleanups disconnect them; the server removes the player) and reset the HUD store (`resetSession`), so the next match starts clean. Esc / F1 work only in the match view. Modals and the HUD action bar opt back into pointer events (`.hud` / `.overlay` are click-through), and the modals scroll inside the window.

### Gameplay + textures revision (owner, 2026-10-10)

31. **Reconciliation toggle moved from `R` to `C`** so `R` can be reload (owner decision). Changed in `NetworkLab`, `CompareView`, the `ComparePane` chip (label `C`), `ControlsOverlay` and the Custom preset caption. The pane chip `C` sits next to pane letters A–D; its tooltip says "Reconciliation [C]".
32. **Phase 2.5 before Phase 3**: weapons, ammo/reload, power-ups, maps, avatar and sound (`GAMERULES.md` §3, §6–§6b, §17, §18) are built before the sync models, so Phase 3's encoders and bandwidth baseline cover the final game state. The `lab` room/Compare view stays movement-only on the `neon` map, so Phase 2 demos and numbers are unaffected.
33. **Weapon numbers** (handgun 8/300 ms/1.2 s, rifle 30/100 ms/1.5 s, shotgun 5 shells × 3 pellets in a 20° fan/700 ms/1.0 s, 0.6 s pellet range — 3 pellets per the owner) and **power-up numbers** (10 s weapons, 6 s × 1.5 speed, one-hit shield, 20 s pad respawn) are first guesses chosen by the agent for a 3-minute match; tune them in `game.json` after play-testing. The shotgun fan is fixed (not random) so client and server never need shared RNG state.
34. **Pickups are never predicted** by the client; the server decides (lowest id wins a same-tick tie). Ammo and reload *are* predicted for the local player and reconciled. Speed enters prediction only once the server confirms it, giving a small, intended correction right after pickup.
35. **Assets** (T50/T51): `NoBu-Shooter/assets/` is tracked in git (≈ 11 MB). Unused parts of the supplied packs were removed (flashlight/knife/melee/walk frames, lighting maps, glass-break), the 2048 px beige floor was downscaled to 1024 px, sounds were trimmed to the useful part and converted to mono 16-bit WAV (no encoder available without installing one; `.ogg`/`.mp3` files kept as supplied). Two pickup badges (Spread Shot from a shell sprite, Speed from a 3D bolt model projected to 2D) were rendered with the local Chrome in headless mode to match the ring-icon set.

### Phase 2.5 implementation (2026-10-10, T52–T56)

36. **Weapon timers advance per consumed input, not per server tick** (`shared/src/sim/combat.ts`): ammo, reload, cooldown, power-up weapon and Speed timers step once per input on the server and in the client's prediction, exactly like movement. Replaying the unacknowledged inputs on top of `snap.me` therefore reproduces the server bit for bit (harness: 0 corrections on a clean link, `tests/netcode.test.ts`). Side effect: a client that stops sending inputs also freezes its own reload and power-up timers — acceptable, it isn't playing. Spawn protection and respawn stay per tick (not predicted).
37. **Fire is sent while held; reload is sticky.** The old client gated `f` on its own cooldown; now both ends apply cooldown and magazine from the same function, so `f` = button state. `r` is repeated on every input of a predicted reload so one lost input can't cancel it (the server ignores it while reloading or full).
38. **Weapon state is reconciled even with Reconciliation off** — an ammo counter that never heals would only confuse; the toggle still governs position. A server-side change that arrives with a `PICKUP` event for us is adopted silently (pickups are not predicted), so only real mispredictions flash the HUD.
39. **Player art is a packed atlas** (`assets/packed/player.{png,json}`, `npm run pack-assets`, `pngjs` dev dependency): 245 frames cropped and downscaled to 0.4×, with a per-frame `pivot` at the shoulder line so Phaser animations switch between frames of different sizes without the body jumping. One 2048×1024 texture instead of 245 keeps Compare (one Phaser game per pane) at 60 fps with 4 panes + REF. The generated atlas is committed so a fresh clone needs no tools.
40. **Snapshot growth**: the new per-player fields, `me` and `pickups` take a 4-player main-room snapshot from ≈ 1.58 kB to ≈ 2.14 kB (+36 %, measured over 60 s of a bot match), ≈ 510 kbps at 30 Hz — above Nightmare's 400 kbps cap (≈ 380 kbps before). Quick Match under Nightmare therefore queues more until Phase 3's delta snapshots; this is the Phase 3 full-snapshot baseline. Compare (lab) snapshots grow only by the per-player fields.
41. **Sound**: Phaser WebAudio in Quick Match only (Compare panes use `noAudio`, or every effect would play once per pane); at most 8 voices; other players' sounds fall off linearly to 30 % across the arena; own shots/reloads come from the prediction (the matching server events are skipped while prediction is on). Trim points of the supplied sounds were chosen from loudness envelopes; check by ear.
42. **Map rotation override** `NOBU_MAPS=plaza,neon npm run demo` (server environment, unknown names ignored) for rehearsals and screenshots; the lab room is always `neon`. Pickup kinds come from a separate seeded PRNG so they don't disturb spawn tie-breaking.

### Power-up rework and developer toggle (owner, 2026-10-10, T58–T60)

43. **Power-up numbers**: weights Speed 4, Dash 3, Spread Shot 2, Shield 2, Piercing 2, Rapid Fire 1 (owner: rifle rarer, Speed more often); Piercing 8 s; Dash 10 s with a 150 ms × 3 burst (≈ 90 px) and a 2 s cooldown; refill 10 s (owner choice). First guesses, tunable in `game.json`. Owner chose both Piercing and Dash to replace Ammo.
44. **"1 + 1 magazines" = a reserve of one magazine**: a manual reload moves only the missing rounds, so the total is always exactly two magazines; the weapon reverts the moment the last round is fired with an empty reserve (rifle ≈ 7.4 s, shotgun ≈ 7.3 s of continuous fire — both before the 10 s timer).
45. **Random spots** are drawn from the room's power-up PRNG: inside a 40 px edge margin, ≥ 24 px from obstacles (every such spot is reachable — tested on 200 samples per map), outside HUD keep-out zones (score, timer, scoreboard, button bar, weapon panel — a power-up spawned under the LEAVE MATCH bar in the first browser check), and preferably ≥ 160 px from other power-ups / ≥ 80 px from alive players. The cap counts every participant, bots included; when it drops, the oldest extras disappear.
46. **Dash prediction**: `d` is repeated during the predicted burst (like `r`) and a dash needs a movement key, so the client and server agree on every input (harness: 0 position corrections while dashing on a clean link). Bots never dash.
47. **Developer toggle** is enabled by environment variables that only `scripts/demo.mjs` sets (`NOBU_DEV=1` for the server, `VITE_NOBU_DEV=1` for Vite); without them the client hides the switch and the server ignores `dev` messages, so tests, smoke and any non-demo server are unaffected. Invincible players still show hits (`PROJECTILE_HIT`) and their name tag reads `[DEV]` for everyone, so a demo audience isn't misled.
48. **Colour rings**: none in Compare (the ghost and truth rings already mark positions); in Quick Match the local player's ring is hidden while the ghost is shown (it sits on the same spot when prediction is right).

### Phase 3: sync models (2026-10-10, `docs/PHASE3_PLAN.md` D1–D10)

49. **One sync model per connection**, chosen in `hello.sync` and switchable live with `sync`: the server swaps the connection's encoder, the player stays (same id, no respawn), and the next message is self-contained. The same model again keeps the encoder (and its delta base). Spectators always get full snapshots — the reference pane is the plain truth.
50. **Encoders live in the connection layer** (`server/src/core.ts`): the room builds one `MsgSnap` object per player every 2 ticks and hands it over with a velocity table; the connection's encoder turns it into `snap`, `snapDelta`, `state` or nothing. Every model therefore sees the same world at the same ticks. Velocity = the entity's movement over the last tick × 60 (exact for players and movers); a jump > 30 px in one tick (respawn, perturb) counts as 0.
51. **Delta = field-level diff against the newest acknowledged snapshot**, if the server still has it (32-snapshot ring) and it is ≤ 1 s old; otherwise a complete `snap` (a *fallback*, counted only after the first ack). Acks ride on `input.sa`, or go alone as `snapAck` when no input message is sent. Removed optional fields are listed in `del` (not sent as `null`: `match.results` is legitimately `null`). The client keeps 64 decoded snapshots, rejects a delta whose base it lacks, and appends new entities at the end (consumers look entities up by id, so the order may differ from the server's).
52. **The delta encoder keeps its own log of unconfirmed events** and repeats them in every delta and fallback until an acknowledged snapshot contained them. The first version limited the base age to the room's 500 ms event window instead; in the smoke test under Nightmare (RTT ≈ 300 ms + jitter + burst loss) late acks then forced full snapshots, which filled the 400 kbps queue, which delayed the next acks — a loop that left the delta client sending full snapshots with a worse ack delay than the full client (685 vs 656 ms). With the log and a 1 s base age: ≈ 200 deltas in 8 s, ack delay ≈ 335 ms vs ≈ 550–610 ms for full.
53. **No rounding**: all models send exact values. Rounding positions to 0.1 px would only move delta from 19 % to 17 % of full (the savings come from omitting unchanged fields), and rounded own positions would cause a tiny correction on every snapshot.
54. **State sync sends complete records plus velocity** at 10 Hz (default) or 30 Hz, not delta-compressed: its point is latency, not bytes. At 10 Hz it costs ≈ 1/3 of full; at 30 Hz slightly more than full (velocities added).
55. **Extrapolation** (`client/src/net/extrapolate.ts`): remote entities are drawn at the estimated current server time with no interpolation delay; position = last state + v·dt with dt clamped to [−100, 250] ms, players pushed out of walls, and the jump at each new state blended away with a 100 ms half-life (snap instead on a life change or ≥ 64 px). The first version clamped dt at 0: a state slightly newer than the render clock then looked like a backward jump on every update, and at 30 Hz the blend offsets piled up into *extra* lag (122 ms at 30 Hz vs 77 ms at 10 Hz in the harness); with back-projection the harness reads Full 150 ms, State 10 Hz 53 ms, State 30 Hz 50 ms mover lag at 50 ms one-way. The Interpolation toggle does nothing in State mode (greyed out). After 250 ms without a state the entity holds still, so heavy burst loss can freeze State 10 Hz briefly.
56. **Bandwidth counts wire bytes** (payload + 28 B per message, the emulator's accounting) in every client metric (Lab tile, pane bars, dock, chart), so the chart's cap line and the measured kbps agree. Phase 1/2 readings rise by ≈ 7 kbps (30 messages/s × 28 B).
57. **Measured** (exit criterion: delta ≤ 40 % of full in the baseline lab scene — met): harness, lab with 4 players + 4 movers on a clean link: delta ≤ 40 % checked, ≈ 19 % in the planning measurement (1.85 kB / 451 kbps → 355 B / 92 kbps with 3 players); browser at Nightmare: 398 vs 59 kbps (15 %); main room (bots firing) through the emulator under Nightmare: 40–56 % of the bytes *received* — full is already squeezed by the 400 kbps cap there, so the received ratio understates the saving. The emulator applies loss before the bandwidth cap, so under Nightmare (12 % loss) full's ≈ 451 kbps reaches the cap as ≈ 400 kbps and its queue builds slowly: give the Sync preset ≈ 15 s (browser: ack delay ≈ 740 vs 310 ms, mover lag ≈ 640 vs 250 ms).
58. **Off-path %**: frames where a moving mover is drawn more than 3 px from every point of its path within the searched delays (−250…1500 ms) — the overshoot and rubber-banding of extrapolation, which a delay can't describe. Interpolated panes read ≈ 0 %; State 10 Hz ≈ 25–35 %, 30 Hz ≈ 8–12 % on zigzag + reversal. Computed only for frames where no delay matched, so it costs nothing on normal frames.
59. **Compare/Quick Match UI**: the Sync preset has no REF pane (3 panes leave a grid cell for the dock with the table and the bandwidth chart; with REF the 2 × 2 grid is full and the dock disappears — the truth rings in each pane still show the real mover positions). Narrow docks (< 700 px) keep ACK, ↓ KBPS, MOVER LAG and OFF-PATH when sync models differ. Quick Match: Network Lab → SYNC MODEL (`Y`), default Full (owner), remembered in the browser's settings. `Y` was the only free key; Vimium maps it to "copy URL" (README troubleshooting).
