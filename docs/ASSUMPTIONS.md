# NoBu Shooter — Implementation Decisions & Assumptions

Decisions that are not obvious from the code, one line each with the reason. Originally required by the v1 spec (`docs/archive/SPEC-v1.md` §3); kept for all later phases (`PHASES.md`).

---

### Architectural & Simulation Assumptions

1. **Monorepo Layout**: Built with npm workspaces under `./NoBu-Shooter` (`shared`, `server`, `emulator`, `client`) with root convenience proxies so commands like `npm run demo`, `npm test`, and `npm run smoke` operate smoothly from either root or project directory.
2. **Fixed Timestep & Determinism**: The game simulation strictly runs at 60 Hz (`dt = 1/60`) using integer key masks and normalized diagonal vectors (`Math.SQRT1_2`) without trig in the player movement path to prevent phantom prediction discrepancies. Since Phase 6 the movers follow the same rule: their paths use only + − × ÷, `Math.sqrt` and a deterministic `dsin` / `dcos` (`shared/src/sim/dtrig.ts`), because browsers and Node do not agree on `Math.cos` to the last bit (#99).
3. **Transport Semantics**: WebSockets transport JSON messages where each text frame is treated as an independent datagram by the network emulator pipeline, with 28 simulated header bytes added for bandwidth calculation. Since Phase 5 the same messages also travel over real UDP (network players), in datagrams of at most 1200 B (#86).
4. **Art and Asset Pipeline**: In accordance with the prompt ("do not generate textures and models, leave them as references and add comments to mark the spot"), all game visuals are rendered procedurally via Phaser 3 Graphics with explicit `/* TEXTURE: <name> */` comments marking integration points for future custom sprites.
5. **Bot Execution Model**: Bots are simulated server-side and feed identical input structures into room authority without network latency; their *input* bypasses the emulator, but their *state* reaches each client through it like any remote player. **Network players** (Phase 5, `npm run swarm`, #89) are the counterpart: they run the same decision code client-side and their own UDP traffic crosses the emulator.
6. **Reconciliation Error Smoothing**: Prediction errors below `epsilonPx` (0.01 px) are ignored; errors between 0.01 px and 64 px are exponentially decayed via `smoothHalfLifeMs` (80 ms); errors exceeding 64 px execute an instantaneous snap.
7. **Event Redundancy**: Server snapshots redundantly retransmit game events from the preceding 500 ms; clients track and deduplicate events by unique `eid`.
8. **Browser Port Alignment**: Client Vite dev server runs on port 5173, Game Server on port 8080 (WS) and 8081 (UDP, Phase 5), Emulator routes on 9000 (WS) and 9100 (UDP), and the emulator's dashboard + control API on 9001.

### Phase 1 decisions (2026-10-09)

9. **Input sending (redundancy off)**: every input is sent exactly once, in the next 30 Hz message after it is created (2 inputs per message). Sending only the newest input — the v1 behaviour — silently dropped half the inputs and caused corrections on a perfect network.
10. **Reorder delay default 80 ms**: a reordered input packet only acts like loss if it arrives after a newer input was already consumed, which needs a delay above the send interval + one tick (~50 ms). With the v1 default (40 ms) the server's sorted input queue absorbed reordering completely, so the effect could not be demonstrated. Covered by `tests/netcode.test.ts`.
11. **Interpolated alive/dead state**: remote players' alive flag comes from the interpolated snapshot pair (not the latest snapshot), so a remote player doesn't vanish ~100 ms before the projectile that killed them reaches them on screen. Respawns (life change) are never interpolated across the arena.
12. **Input → Screen definition**: prediction on = time from the input sample to the presentation of the next frame (sample → render + one frame). Prediction off = ack delay (input creation → snapshot acknowledging it) + interpolation delay (if on) + one frame. "Ack delay" is shown alongside.
13. **Server loop on Windows**: OS timers fire every ~15.6 ms on Windows (measured for both `setTimeout` and `Atomics.wait`), so the loop sleeps one timer quantum and yields with `setImmediate` only for the final ~1 ms before each tick: ~1 % CPU instead of a fully spun core, tick rate unchanged (60–61 Hz).
14. **Process lifetime**: services run as single node processes (`node --import tsx`, Vite via its JS API) and exit by themselves when the launcher's PID (`NOBU_PARENT_PID`) disappears, because Windows does not kill children with their parent.
15. **Emulator session labels**: each `NetClient` connects with a unique label (`<name>-<4 random chars>`), which the UI uses to pick *its own* session from the emulator stats (loss tiles, packet strip). Session RNGs share the CLI seed, which keeps Compare panes under comparable random conditions.
16. **Presets are complete configs**: applying a preset replaces the whole link config (missing fields take defaults), so no setting leaks from the previous preset (e.g. burst loss after Nightmare).
17. **Lab room**: always `RUNNING` with any number of players (GAMERULES.md §14); no spawn protection because firing is disabled there.
18. **Dev-mode warnings**: React StrictMode mounts the Compare view twice in development, producing harmless "WebSocket is closed before the connection is established" warnings (one per pane client, the spectator and the emulator control client); `NetClient` and `EmulatorClient` ignore callbacks from the discarded connection (generation counter / socket identity), so no duplicate control socket or reconnect loop is left behind. Production builds don't double-mount.

### Phase 2 decisions (2026-10-09, `docs/PHASE2_PLAN.md` D1–D7)

19. **Movers are `PlayerSnap` entries** with a `mover` field, kept outside the room's player map (no player cap, no inputs, ids from the player id counter). Interpolation — and later sync models — treat them like any remote player.
20. **Mover paths are pure functions of server time** (`shared/src/sim/movers.ts`, `position = moverPath(pattern, tick / 60)`), continuous (no teleports), 200 px/s, and clear of obstacles by ≥ 20 px (tested). Any client can compute the exact true position at any server time.
21. **True server time comes from the spectator**: Compare always opens a direct (unimpaired) spectator connection; its clock offset (`serverNow() = now + EMA(st − arrival)`) is the truth clock for every pane. Expected error ±1–2 ms (snapshot send times jitter with the Windows timer and the hybrid server loop; the EMA averages it out).
22. **Remote error = delay, not distance**: for each drawn mover, τ is the delay at which the true path passes through the drawn position *heading the same way* (a back-and-forth path passes each point twice). Lag = median τ, wobble = interquartile range / 1.35 (= std-dev for normal noise, robust to rare glitches such as a buffer underrun), plus mean distance (px) and frozen frames (true position moved > 0.5 px, drawn < 0.1 px) over a 2 s window. Raw distance depends on the path's shape (stops, reversals) and would rate interpolation as worse. Measured at 50 ± 30 ms (browser): interpolation off ≈ 75 ± 26 ms, 60–70 % frozen; on ≈ 160 ± 3 ms, 2 % frozen.
23. **Frozen % depends on the display**: at 60 Hz with 30 Hz snapshots, a pane without interpolation repeats every other frame (≈ 50 %, more under jitter); a 144 Hz monitor would show ≈ 79 %.
24. **One shared input driver**: in Compare, `InputDriver` owns the keyboard and a single fixed 60 Hz loop that gives every pane's client the same keys on the same step and flushes all inputs together at 30 Hz. Panes' Phaser scenes only render. Firing is not driven (the lab room rejects it).
25. **Comparison presets change one setting**; their network conditions are complete emulator configs (named or ad-hoc presets), so nothing carries over. "Prediction off vs on" keeps interpolation on in both panes.
26. **Pane layout**: `layoutPanes` tries every rows × cols grid and keeps the largest canvas; canvases are exactly 16:9, so there's no letterboxing (measured 0–0.2 %); leftover space (or an empty grid cell) holds the dock. The network drawer overlays the panes so opening it never resizes them.
27. **Compare rendering performance**: each pane renders at its displayed size (`Phaser.Scale.RESIZE` + camera zoom) instead of a full 1280×720 frame shrunk by CSS; static art (grid, walls) is baked into textures once; mover bodies, trail dots and truth rings are pooled sprites. Phaser re-tessellates every `Graphics` object each frame, which had made 5 panes CPU-bound at 20 fps on the dev laptop's Intel UHD GPU; now 60 fps with 4 panes + reference at 1920×1080. Quick Match keeps `FIT` (unchanged look).

### Bug-fix run merged from branch `game` (2026-10-09, merged 2026-10-10)

28. **Movement keys are page-level** (`client/src/game/input.ts`): in Quick Match one `window` capture-phase listener tracks keys by `KeyboardEvent.code` (physical position: works on AZERTY etc. and while an IME reports `keyCode` 229) and does not skip events another handler already `preventDefault`-ed. Phaser's keyboard is disabled (`input.keyboard: false`): it `preventDefault`s captured keys and ignores already-prevented events, which hid keys from every other listener. Keys are released on window blur / tab hide. Compare's `InputDriver` (#24) uses the same key mapping and text-field rule. Hotkeys (`Tab`, `1`–`5`, `P`/`R`/`I`/`G`, movement) are ignored only in text fields, not on a focused slider or checkbox. A browser extension that intercepts keys before the page (Vimium: `d`, `r`, `p`, digits) still wins; the README's troubleshooting section says how to exclude the demo.
29. **One lab spawn point**: every `lab` player spawns at `rooms.lab.spawn` (880, 360), so every Compare pane's player starts in the same place (players never collide and the lab has no firing). With identical inputs from the `InputDriver`, the server paths are identical (`tests/netcode.test.ts`), so in the REF pane the panes' players overlap. The point is ≥ 108 px from every mover path and clear of obstacles (`tests/movers.test.ts`); the `game` branch had (640, 520), which lies on the zigzag lane. Under loss without input redundancy each link drops different inputs and the players drift apart (~40 px at 10 % in the harness) — the Redundancy comparison preset.
30. **Leaving a match**: **◄ LEAVE MATCH** (HUD) and the Esc menu's **◄ LEAVE MATCH — BACK TO MAIN MENU** drop both clients (their effect cleanups disconnect them; the server removes the player) and reset the HUD store (`resetSession`), so the next match starts clean. Esc / F1 work only in the match view. Modals and the HUD action bar opt back into pointer events (`.hud` / `.overlay` are click-through), and the modals scroll inside the window.

### Gameplay + textures revision (owner, 2026-10-10)

31. **Reconciliation toggle moved from `R` to `C`** so `R` can be reload (owner decision). Changed in `NetworkLab`, `CompareView`, the `ComparePane` chip (label `C`), `ControlsOverlay` and the Custom preset caption. The pane chip `C` sits next to pane letters A–D; its tooltip says "Reconciliation [C]".
32. **Phase 2.5 before Phase 3**: weapons, ammo/reload, power-ups, maps, avatar and sound (`GAMERULES.md` §3, §6–§6b, §17, §18) are built before the sync models, so Phase 3's encoders and bandwidth baseline cover the final game state. The `lab` room/Compare view stays movement-only on the `neon` map, so Phase 2 demos and numbers are unaffected.
33. **Weapon numbers** (handgun 8/300 ms/1.2 s, rifle 30/100 ms/1.5 s, shotgun 5 shells × 3 pellets in a 20° fan/700 ms/1.0 s, 0.6 s pellet range — 3 pellets per the owner) and **power-up numbers** (10 s weapons, 6 s × 1.5 speed, one-hit shield, 20 s pad respawn) are first guesses chosen by the agent for a 3-minute match; tune them in `game.json` after play-testing. The shotgun fan is fixed (not random) so client and server never need shared RNG state.
34. **Pickups are never predicted** by the client; the server decides (lowest id wins a same-tick tie). Ammo and reload *are* predicted for the local player and reconciled. Speed enters prediction only once the server confirms it, giving a small, intended correction right after pickup.
35. **Assets** (T50/T51): `NoBu-Shooter/assets/` is tracked in git (≈ 11 MB). Unused parts of the supplied packs were removed (flashlight/knife/melee/walk frames, lighting maps, glass-break), the 2048 px beige floor was downscaled to 1024 px, sounds were trimmed to the useful part and converted to mono 16-bit WAV (no encoder available without installing one; `.ogg`/`.mp3` files kept as supplied). Two pickup badges (Spread Shot from a shell sprite, Speed from a 3D bolt model projected to 2D) were rendered with the local Chrome in headless mode to match the ring-icon set.

### Phase 2.5 implementation (2026-10-10, T52–T56)

36. **Weapon timers advance per consumed input, not per server tick** (`shared/src/sim/combat.ts`): ammo, reload, cooldown, power-up weapon and Speed timers step once per input on the server and in the client's prediction, exactly like movement. Replaying the unacknowledged inputs on top of `snap.me` therefore reproduces the server bit for bit (harness: 0 corrections on a clean link, `tests/netcode.test.ts`). Side effect: a client that stops sending inputs also freezes its own reload and power-up timers — acceptable, it isn't playing. Spawn protection and respawn stay per tick (not predicted).
37. **Fire is sent while held; reload is sticky.** The old client gated `f` on its own cooldown; now both ends apply cooldown and magazine from the same function, so `f` = button state. `r` is repeated on every input of a predicted reload so one lost input can't cancel it (the server ignores it while reloading or full).
38. **Weapon state is reconciled even with Reconciliation off** — an ammo counter that never heals would only confuse; the toggle still governs position. A server-side change that arrives with a `PICKUP` event for us is adopted silently (pickups are not predicted), so only real mispredictions flash the HUD.
39. **Player art is a packed atlas** (`assets/packed/player.{png,json}`, `npm run pack-assets`, `pngjs` dev dependency): 245 frames cropped and downscaled to 0.4×, with a per-frame `pivot` at the shoulder line so Phaser animations switch between frames of different sizes without the body jumping. One 2048×1024 texture instead of 245 keeps Compare (one Phaser game per pane) at 60 fps with 4 panes + REF. The generated atlas is committed so a fresh clone needs no tools.
40. **Snapshot growth**: the new per-player fields, `me` and `pickups` take a 4-player main-room snapshot from ≈ 1.58 kB to ≈ 2.14 kB (+36 %, measured over 60 s of a bot match), ≈ 510 kbps at 30 Hz — above Nightmare's 400 kbps cap (≈ 380 kbps before). Quick Match under Nightmare therefore queues more until Phase 3's delta snapshots; this is the Phase 3 full-snapshot baseline. Compare (lab) snapshots grow only by the per-player fields.
41. **Sound**: Phaser WebAudio in Quick Match only (Compare panes use `noAudio`, or every effect would play once per pane); at most 8 voices; other players' sounds fall off linearly to 30 % across the arena; own shots/reloads come from the prediction (the matching server events are skipped while prediction is on). Trim points of the supplied sounds were chosen from loudness envelopes; check by ear.
42. **Map rotation override** `NOBU_MAPS=plaza,neon npm run demo` (server environment, unknown names ignored) for rehearsals and screenshots; the lab room is always `neon`. Pickup kinds come from a separate seeded PRNG so they don't disturb spawn tie-breaking.

### Power-up rework and developer toggle (owner, 2026-10-10, T58–T60)

43. **Power-up numbers**: weights Speed 4, Dash 3, Spread Shot 2, Shield 2, Piercing 2, Rapid Fire 1 (owner: rifle rarer, Speed more often); Piercing 8 s; Dash 10 s with a 150 ms × 3 burst (≈ 90 px) and a 2 s cooldown; refill 10 s (owner choice; 7 s since 2026-10-11, #82). First guesses, tunable in `game.json`. Owner chose both Piercing and Dash to replace Ammo.
44. **"1 + 1 magazines" = a reserve of one magazine**: a manual reload moves only the missing rounds, so the total is always exactly two magazines; the weapon reverts the moment the last round is fired with an empty reserve (rifle ≈ 7.4 s, shotgun ≈ 7.3 s of continuous fire — both before the 10 s timer).
45. **Random spots** are drawn from the room's power-up PRNG: inside a 40 px edge margin, ≥ 24 px from obstacles (every such spot is reachable — tested on 200 samples per map), outside HUD keep-out zones (score, timer, scoreboard, button bar, weapon panel — a power-up spawned under the LEAVE MATCH bar in the first browser check), and preferably ≥ 160 px from other power-ups / ≥ 80 px from alive players. The cap counts every participant, bots included; when it drops, the oldest extras disappear.
46. **Dash prediction**: `d` is repeated during the predicted burst (like `r`) and a dash needs a movement key, so the client and server agree on every input (harness: 0 position corrections while dashing on a clean link). Bots never dash.
47. **Developer toggle** is enabled by environment variables that only `scripts/demo.mjs` sets (`NOBU_DEV=1` for the server, `VITE_NOBU_DEV=1` for Vite); without them the client hides the switch and the server ignores `dev` messages, so tests, smoke and any non-demo server are unaffected. Invincible players still show hits (`PROJECTILE_HIT`) and their name tag reads `[DEV]` for everyone, so a demo audience isn't misled.
48. **Colour rings**: none in Compare (the ghost and truth rings already mark positions); in Quick Match the local player's ring is hidden while the ghost is shown (it sits on the same spot when prediction is right).

### Phase 3: sync models (2026-10-10, `docs/PHASE3_PLAN.md` D1–D10)

49. **One sync model per connection**, chosen in `hello.sync` and switchable live with `sync`: the server swaps the connection's encoder, the player stays (same id, no respawn), and the next message is self-contained. The same model again keeps the encoder (and its delta base). Spectators always get full snapshots — the reference pane is the plain truth.
50. **Encoders live in the connection layer** (`server/src/core.ts`): the room builds one `MsgSnap` object per player every 2 ticks and hands it over with a velocity table; the connection's encoder turns it into `snap`, `snapDelta`, `state` or nothing. Every model therefore sees the same world at the same ticks. Velocity = the entity's movement over the last tick × 60 (exact for players and movers); a jump > 30 px in one tick (respawn, perturb) counts as 0.
51. **Delta = field-level diff against the newest acknowledged snapshot**, if the server still has it (32-snapshot ring) and it is ≤ 1 s old; otherwise a complete `snap` (a *fallback*, counted only after the first ack). Acks ride on `input.sa`, or go alone as `snapAck` when no input message is sent. Removed optional fields are listed in `del` (not sent as `null`: `match.results` is legitimately `null`). The client keeps 64 decoded snapshots, rejects a delta whose base it lacks, and appends new entities at the end (consumers look entities up by id, so the order may differ from the server's).
52. **The delta encoder keeps its own log of unconfirmed events** and repeats them in every delta and fallback until an acknowledged snapshot contained them. The first version limited the base age to the room's 500 ms event window instead; in the smoke test under Nightmare (RTT ≈ 300 ms + jitter + burst loss) late acks then forced full snapshots, which filled the 400 kbps queue, which delayed the next acks — a loop that left the delta client sending full snapshots with a worse ack delay than the full client (685 vs 656 ms). With the log and a 1 s base age: ≈ 200 deltas in 8 s, ack delay ≈ 335 ms vs ≈ 550–610 ms for full.
53. **No rounding**: all models send exact values. Rounding positions to 0.1 px would only move delta from 19 % to 17 % of full (the savings come from omitting unchanged fields), and rounded own positions would cause a tiny correction on every snapshot.
54. **State sync sends complete records plus velocity** at 10 Hz (default) or 30 Hz, not delta-compressed: its point is latency, not bytes. At 10 Hz it costs ≈ 1/3 of full; at 30 Hz slightly more than full (velocities added).
55. **Extrapolation** (`client/src/net/extrapolate.ts`): remote entities are drawn at the estimated current server time with no interpolation delay; position = last state + v·dt with dt clamped to [−100, 250] ms, players pushed out of walls, and the jump at each new state blended away with a 100 ms half-life (snap instead on a life change or ≥ 64 px). The first version clamped dt at 0: a state slightly newer than the render clock then looked like a backward jump on every update, and at 30 Hz the blend offsets piled up into *extra* lag (122 ms at 30 Hz vs 77 ms at 10 Hz in the harness); with back-projection the harness reads Full 150 ms, State 10 Hz 53 ms, State 30 Hz 50 ms mover lag at 50 ms one-way. The Interpolation toggle does nothing in State mode (greyed out). After 250 ms without a state the entity holds still, so heavy burst loss can freeze State 10 Hz briefly.
56. **Bandwidth counts wire bytes** (payload + 28 B per message, the emulator's accounting) in every client metric (Lab tile, pane bars, dock, chart), so the chart's cap line and the measured kbps agree. Phase 1/2 readings rise by ≈ 7 kbps (30 messages/s × 28 B).
57. **Measured** (exit criterion: delta ≤ 40 % of full in the baseline lab scene — met): harness, lab with 4 players + 4 movers on a clean link: delta ≤ 40 % checked, ≈ 19 % in the planning measurement (1.85 kB / 451 kbps → 355 B / 92 kbps with 3 players); browser at Nightmare: 398 vs 59 kbps (15 %); main room (bots firing) through the emulator under Nightmare: 40–56 % of the bytes *received* — full is already squeezed by the 400 kbps cap there, so the received ratio understates the saving. The emulator applies loss before the bandwidth cap, so under Nightmare (12 % loss) full's ≈ 451 kbps reaches the cap as ≈ 400 kbps and its queue builds slowly: give the Sync preset ≈ 15 s (browser: ack delay ≈ 740 vs 310 ms, mover lag ≈ 640 vs 250 ms).
58. **Off-path %**: frames where a moving mover is drawn more than 3 px from every point of its path within the searched delays (−250…1500 ms) — the overshoot and rubber-banding of extrapolation, which a delay can't describe. Interpolated panes read ≈ 0 %; State 10 Hz ≈ 25–35 %, 30 Hz ≈ 8–12 % on zigzag + reversal. Computed only for frames where no delay matched, so it costs nothing on normal frames.
59. **Compare/Quick Match UI**: the Sync preset has no REF pane (3 panes leave a grid cell for the dock with the table and the bandwidth chart; with REF the 2 × 2 grid is full and the dock disappears — the truth rings in each pane still show the real mover positions). Narrow docks (< 700 px) keep ACK, ↓ KBPS, MOVER LAG and OFF-PATH when sync models differ. Quick Match: Network Lab → SYNC MODEL (`Y`), default Full (owner), remembered in the browser's settings. `Y` was the only free key; Vimium maps it to "copy URL" (README troubleshooting).

### Phase 4: Presenter mode + polish (2026-10-11, `docs/PHASE4_PLAN.md` D1–D11)

60. **Presenter steps are complete states** (D2): a Quick Match step sets the emulator (a named or ad-hoc preset applied to `all`, like keys `1`–`5`), all five netcode toggles and the sync model; a Compare step selects a Compare preset. `N`/`B` therefore always land on the same state, whatever was pressed in between; manual changes last until the next step. One-off actions (the Q9 nudge) run each time the step is *entered*. Commands sent before the emulator control socket is open are lost, so the step is re-applied once it connects. The presenter's sync and toggle changes are not saved as the user's preferences (only the Lab's own `Y` is).
61. **Presenter keys `N` / `B` / `H`** are read by `KeyboardEvent.code` (layout-independent, like movement) and ignored with Ctrl/Alt/Meta, auto-repeat and in text fields; they are not game actions (GAMERULES.md). The bar's buttons don't take focus, so `Space` (dash) can't press them again. The bar sits in the layout flow (under the arena / the Compare grid) rather than over it (plan deviation Z1), so it never hides what it describes; `H` returns the space. Invincible is switched on by the Quick script (D3) and off again on END / Leave / Exit; without `npm run demo` the bar says so and the script still runs.
62. **Expected numbers on the bar are measurements with ranges**, not targets. Under Nightmare the full-snapshot queue depends on the map and the fight (snapshot size 1.3–2.1 kB): in the Phase 4 shots after ≈ 15 s the queue read ≈ 100–170 ms and the ack delay ≈ 540–580 ms (Phase 3's browser check: ≈ 650–740 ms); Q10's line says "≈ 550–700 ms".
63. *(Removed 2026-10-11, #84.)* **Bloom = one Phaser camera post-FX pass with a single blur step** (`addBloom(0xffffff, 2, 2, 1, 0.7, 1)`), Quick Match only (D6), at Graphics Quality *high* on WebGL. Measured on the dev laptop's Intel UHD (headless Chrome uses it via ANGLE/D3D11) at 1920 × 1080: no bloom 60 fps; 4 blur steps 28–32 fps; 2 steps 38; **1 step 57–60** (kept; the 2 px offset widens the glow at no cost). The auto-off watches the frame times of the last `fpsDegrade.forSeconds` (3 s) while bloom is on; below `minFps` (45) it removes the pass for the rest of the match (until the quality setting changes) and logs one `console.info`.
64. **Full-screen modals have no backdrop blur**: blurring the live (bloomed) WebGL arena every frame dropped Settings / Controls to 29–31 fps at 1920 × 1080, enough to trip the bloom auto-off after 3 s. A 90 % solid backdrop looks the same and keeps 51–55 fps.
65. **Arena polish is baked, not loaded** (no new assets): the death ✕ (`death-x`, tinted with the victim's colour, fades over `respawnDelayMs`, pooled), the remote aim chevron (`aim-chevron`, Quick Match only — Compare panes have no colour rings either) and the respawn pulse (two expanding rings, 700 ms) for every player, detected from the snapshot's `life` counter / `alive` flag.
66. **Lab sections** fold by their titles; the open state is remembered per section (`labSections` in the browser's settings). Defaults (D8): Presets, Sync model, Netcode toggles, Live metrics open; Impairment sliders, Developer, Sparklines, Notes closed; a closed section shows a one-line summary (e.g. `120±50 ms · 12 % · 400 kbps`). Short screens tighten rows (≤ 920 px) and use 3-column metric tiles (≤ 800 px). Measured: no Lab scroll at 1920 × 1080 (100/115/130 %), 1600 × 900 and 1280 × 720 (100 %). Compare's network drawer never folds its sections.
67. **UI scale** (100 / 115 / 130 %) sets `--ui-scale` on `:root`, which drives the root font size (all rem-based UI) and the Lab width; the arena canvas is not scaled (it already fills its area). Fixed-pixel elements (canvas strips, Compare's 44 px top bar) stay as they are.
68. **The packet strip replays packets on their real timelines**: each dot enters the EMULATOR box at the event's `t` and crosses it for `delayMs`, drawn a smoothed lag behind real time (the worst arrival delay of the last 2 s + travel, 250–2200 ms) — a jitter buffer, so a delivered event, which the emulator only reports after delivery, can still be drawn from the moment it arrived. Consequences: reordered packets (white ring) are visibly overtaken by later ones, a growing queue shows as dots crowding the box, and the strip runs ≈ 0.3 s behind at Baseline and ≈ 1 s behind under Nightmare. It assumes the emulator and the browser share a clock (same machine, as in every demo setup). Duplicates are drawn as a split flash at the box entry; the two delivered copies are ordinary dots (the old strip added two extra synthetic dots).
69. **Queue depth** is `max(0, freeAt − now)` of the bandwidth stage per link (the emulator's FIFO model), reported at 2 Hz in `stats` and eased in the strip; the bar is scaled to `queueLimitMs` (tail-drop point) and turns red above 75 %.
70. **`npm run shots`** uses `playwright-core` **1.48.2** (exact pin, the version used for all browser checks since Phase 1) as a devDependency of `NoBu-Shooter`, with the installed Chrome (`channel: 'chrome'`, or `NOBU_CHROME`) — no browser download, nothing global. Every screen gets a fresh browser context (clean `localStorage`; resizing a live headless page gave shifted shots in Phase 3). Headless Chrome on this laptop renders with the real GPU, so the recorded fps are meaningful (± a few fps from the screenshot itself).
71. **Phaser games release their WebGL context** when a view closes (`GameContainer`, `WEBGL_lose_context` 0.5 s after `game.destroy`). Phaser only drops its reference, so contexts lived until garbage collection; switching Quick Match ↔ Compare 6 times (Compare = up to 5 games, doubled by React StrictMode in development) hit Chrome's limit of 16 and it force-lost the oldest ("Too many active WebGL contexts"). After the fix, 8 rounds of switching gave no "Too many" warning. (A `Framebuffer status: Incomplete Attachment` seen in one Phase 4 run was first attributed to this; its real cause was found later — #80.)
72. **Sound teardown**: our sound-finished handler destroys the Phaser sound in a microtask. Destroying it inside the STOP event (emitted by Phaser's own destroy during game teardown, before the sound is marked removed) nulled its audio nodes mid-way and threw on leaving a match after sounds had played (found in Phase 4, present since Phase 2.5).

### Owner revision after Phase 4 (2026-10-11, `log.md` T76–T82)

73. **SYNC MODEL stays one choice** (owner chose "regroup UI"): a connection receives exactly one stream, so the four chips are shown as two labelled groups — Snapshots (interpolated): Full, Delta; State sync (extrapolated): 10 Hz, 30 Hz — with exactly one lit. Independent "encoding × model" choices (e.g. delta-compressed state) were offered and declined.

A map switch restarts the game on that map but keeps the talk on its step (state re-applied, step timer restarted, one-off actions like the Q9 nudge not repeated). Neither advances the normal map rotation.

The drone paths were laid out for Neon; on Warehouse, Plaza and Overgrown three of them pass over props — they are scripted drones without collision, so this is only visual. 77. **Countdown fix (pre-existing since Phase 1)**: `startCountdown` marked players dead "so they can't move", but the tick's respawn step revived them at once with `life = 1` at another spawn point, and `startMatch` moved them again. A player who hadn't died in the previous match therefore kept `life = 1`, and their client showed the move as a correction of hundreds of px (hidden behind the results overlay until RESTART made it visible). Now the countdown keeps players alive at their spawn with `life + 1` (movement is ignored outside RUNNING anyway) and the match starts from there: clients hard-reset, no correction, no second jump at GO (harness test: restart under 50 ms + 10 % loss gives no correction ≥ 64 px, main and lab).
78. **Give power-up** applies the power-up on the server exactly like a pickup and emits the same `PICKUP` event, so the client adopts the new weapon state silently (pickups are never predicted). Only for an alive player in a running match of a room with power-ups (not the lab).
79. **Truth ring (owner question)**: in Compare the dashed ring is the drone's true position *now* (server time); the drawn drone is where the pane's client shows it — interpolated 100 ms in the past plus the network delay — so with snapshot sync the drawn drone trails *behind* its ring. That is the effect being demonstrated (mover lag). With State sync the drawn drone is extrapolated forward and can overshoot *ahead* of the ring at turns. The TRUTH button's tooltip now says so.

Short screens (≤ 800 px) also hide the SYNC MODEL hint line and keep metric values on one line, so the default Lab still fits 1280 × 720 with the two sync groups.

### Phase 5: realistic transport + standalone emulator (2026-10-12, `docs/PHASE5_PLAN.md` D1–D15)

85. **The emulator is game-agnostic in code, not only in spirit.**
    - Payloads are opaque bytes: WS binary frames stay binary, and UDP datagrams are forwarded unchanged.
    - The PRNG is a local copy, `@nobu/shared` is gone from `emulator/package.json`, and a test fails if `emulator/src` imports anything from the game.
    - `Packet.data` is `Buffer | string`: the in-process netcode harness and the old tests still pass text, and the pipeline treats both alike (plan deviation, §8 of the plan).
86. **Fragments at 1200 B, at the application layer** (owner choice).
    - Full snapshots cannot be trimmed under 1200 B: 1.3 kB on an idle map, ≈ 3 kB on average in a 4-way fight (2.7 fragments), up to ≈ 4.5 kB (4 fragments) during heavy fire with projectile-hit events.
    - Fragments are ASCII-headed (`~id.i/n|`) so the packet log stays readable. The emulator impairs each one, so a k-fragment message survives with (1 − p)^k. Tested: 2 fragments at 10 % loss arrive ≈ 81 % of the time.
    - Delta and state messages almost always fit one datagram, which gives delta a second advantage over full on lossy UDP links.
87. **Routes own their defaults per direction.** A change for one direction on a route (or on `all`) is stored for that direction only, so sessions that join later get it the same way.
    - Found by the browser check: with a single default config, "up only, 20 %" reached later sessions in both directions (42 % round-trip loss instead of ≈ 20 %).
    - `state.defaults` (the up link, as before) plus a new `defaultsDown`.
88. **The game impairs only its own route (`ws:9000`)** (owner choice). The Network Lab, Compare and Presenter send `ws:9000` where they sent `all`; `EmulatorClient.routeView` gives the UI that route's defaults and preset. Network players keep whatever the dashboard, or Presenter step Q13, gives `udp:9100`.
89. **Network players use the bot brain on their own view.**
    - `shared/src/sim/botBrain.ts` is the server's bot code moved verbatim, reading only `x`, `y`, `alive`, `protectionTicksLeft`; the server bot tests are unchanged.
    - A network player feeds it its predicted self and the interpolated others, so under lag it aims where *it* sees people.
    - Names `UDP-n` (no protocol change). They count as humans in the bot formula, so bots already in a running match stay until the next countdown.
    - Their few clean-link corrections (3–7 px) happen at the moment they die: death is not predicted (seen with `--verbose`); the same holds for browser players.
90. **Network players name their own emulator session.** After the welcome, each one sends `session.label` with its local address (`127.0.0.1:<port>`), so the dashboard shows `UDP-2`, not `udp 127.0.0.1:53114`. The label is remembered for a session re-created after the UDP idle timeout. Without the emulator (`--direct`) nothing is sent.
91. **Only the control port is locked to this machine** (owner revision, T95).
    - The control API can open listeners and forward to any host, so it binds 127.0.0.1 and accepts browsers only from allowlisted Origins; non-browser tools send no Origin and are stopped by the bind instead.
    - Data routes and the server's ports keep listening on all interfaces, so the multiplayer version (`PHASES.md` Phase 7, done: `npm start` serves players on the LAN) isn't blocked. Tests and smoke bind 127.0.0.1.
    - Still not done (Phase 7 M4, future "option B" for internet play; the game server keeps UDP closed unless `--udp`): a return-routability check before the UDP server streams to a new address (a spoofed `hello` could otherwise make it send snapshots to a victim for `timeoutMs`).
92. **UDP sessions are NAT-like and expire.** One session (and one upstream socket) per client `ip:port`; 30 s without traffic in either direction closes it; at most 64 sessions per route, further clients refused and counted. ICMP "port unreachable" errors on upstream sockets are ignored, as a NAT mapping would survive them (tested by starting a client before its target).
93. **UDP readiness checks bind-probe the port.** `waitForPort` uses a TCP connect probe; for UDP, `udpPortInUse` tries an exclusive bind on 0.0.0.0 and 127.0.0.1 (taken = in use). The demo, smoke and shots check all six ports.
94. **Queue-drop delays are whole milliseconds.** Found in the Phase 5 shots: the packet log showed `403.086669921875 ms`, because the pipeline reported the fractional queue wait of a `dropped-queue` event unrounded since Phase 1 (the Phase 4 strip only used it for drawing). Now rounded, with a test.
95. **Piercing rounds are purple** (owner, 2026-10-12, T96). They were tinted lavender with a multiply tint, which on the yellow `fx/bullet.png` came out olive. Now the core is tint-filled light purple (0xd8a8ff), with a purple halo and a stronger purple trail (0xa23cff).
96. **The dashboard renders untrusted text safely.** Session labels (`?label=`) and payload previews come from arbitrary traffic, so the dashboard builds every row with `textContent`, never `innerHTML`. It loads nothing from the network (no fonts, no CDN), so it also works offline.

### Phase 6: lockstep (2026-10-12, `docs/PHASE6_PLAN.md` D1–D12)

97. **Lockstep is the lab room only, and server-relayed.**
    - The lab is the deterministic subset (movement only, no bots, no firing, no clock). Making the match replayable is out of scope; `sync: lockstep` elsewhere → `error LOCKSTEP_LAB_ONLY` (not fatal).
    - The server stays the clock and the authority and never waits for anyone: what it relays is the keys it *consumed* per tick, so a late input simply didn't move that player, exactly as in the other models. Peer-to-peer lockstep (everyone waits for the slowest) would need peers and a pause protocol.
98. **Keyframes travel inside the tick stream.** Anything inputs don't explain (join, leave, nudge, RESTART, map, movers) makes the next tick's record a keyframe of the whole lab world, so loss recovery (NACK or the redundant window) covers it like any other tick. A keyframe is ≈ 100–300 B.
99. **Determinism is checked, and the check paid off.** Every 30 ticks the server sends a hash of its world; a mismatch counts a desync and asks for a keyframe.
    - The first browser check found 1 desync per lockstep pane in 30 s: Chrome and Node 26 differ in the last bit of `Math.cos` / `Math.sin` for ≈ 3.4 % of the circle drone's angles (13 631 of 400 000 values, measured with both engines).
    - Fix: `dsin` / `dcos` built from fdlibm's kernel polynomials and a two-part π/2 reduction (only + − × ÷ and `Math.round`, which IEEE 754 and ECMAScript define exactly, and JavaScript never fuses a multiply-add) — 0 of 400 000 values differ between the engines, and they stay within 1e-12 of `Math`. `Math.hypot` (also not exact) was replaced by `Math.sqrt` in the mover paths. Players were never affected: `stepPlayer` uses only exact operations.
    - After the fix: 0 desyncs in 60 s in the browser, in every test and in smoke step 8.
100. **The Rd chip picks the recovery** (owner choice). Off = each record once, holes asked for again (`lsNack`, retried after 1.5 × RTT, at least 50 ms); on = every message repeats every record after the ack (at most 60 ticks, then a resync). The chip also keeps its Phase 1 meaning (input redundancy) on the same pane.
101. **Playout runs on the server's tick, 2 ticks behind.** The client estimates the server's tick from each message's `tick` (EMA, like the snapshot clock) and shows tick (estimate − 2). Batching sends two ticks per message, so 2 ticks of buffer means batching alone never stalls. A missing tick is a stall; afterwards it catches up with up to 3 ticks per frame (a brief fast-forward). A keyframe further on replaces the missing ticks (counted as a resync).
102. **No prediction in lockstep** (owner choice): the own player moves when its keys come back in a record. Input → Screen ≈ RTT + the playout buffer + the send interval: ≈ 133 ms at 30 ms one-way, ≈ 200–215 ms at 50 ms (Rd on). P / C / I / G are greyed out on lockstep panes; Corrections and Ack show "–".
103. **Lockstep pane metrics**: Stalled (% of frames frozen, 10 s), stalls/s, longest stall, behind (ms behind the estimated server tick), NACKed ticks, desyncs. A frozen render loop would read as "behind", so the netcode tests keep drawing frames while they wait for the metrics.
104. **Measured (Snapshot vs Lockstep, 50 ms + 5 % loss):** the harness: Rd off 21 % stalled vs Rd on 1.8 %; the browser: ≈ 15–30 % vs ≈ 3–5 %, longest ≈ 300–650 ms vs 40–70 ms; smoke step 8 (Node, real sockets): 28.8 % vs 4.6 %. Under 10 % *burst* loss Rd on stalls too (≈ 17 % in the harness): four lost messages in a row outlast the playout buffer whatever the window.
105. **Lockstep bytes are ≈ 1/10 of full, not the planned 5–10 kbps.** An `ls` message with two records for one player is ≈ 95 B of JSON + 28 B overhead at 30 Hz ≈ 30–40 kbps; the per-message overhead alone is 6.7 kbps. Rd on repeats unacknowledged records (≈ one RTT of them), ≈ 2.5–3 × the bytes. A binary encoding would shrink it further; not needed for the demo.
106. **The lockstep pane's snapshot is synthetic.** `NetClient` turns the replayed world into a `snap` (players + movers, no projectiles or events) whenever the shown tick changes, so the arena scene, HUD and mover metrics work unchanged; the ghost is hidden (nothing is predicted).
107. **Quick Match never offers lockstep.** Its SYNC MODEL list and `Y` cycle are unchanged; a stored `lockstep` setting falls back to Full; only Compare's cycle (`COMPARE_SYNC_CYCLE`) adds it.
108. **The Compare view sets pane toggles through `setToggles`** (it used to assign them directly). Found while wiring lockstep: a direct assignment would change the Rd chip without switching the lockstep recovery on the server.
109. **Network players join the talk at Q13, not at the start** (rehearsal finding, 2026-10-12). Started with the demo (`--swarm 3`) they make the match bigger: three UDP shooters plus a bot that stays, because the Presenter stops the match clock. Full snapshots then need ≈ 816 instead of ≈ 475 kbps, and at Nightmare even Delta stays at the 400 kbps cap (Q11 ack ≈ 720 vs ≈ 330 ms). The talk track starts them at Q13 with `npm run swarm -- --n 3`: they appear in ≈ 1 s, and the Q13 bar's hint says so. `npm run shots` still uses `--swarm 2` (it photographs single steps).

### Phase 7: multiplayer readiness, LAN (2026-10-12, `docs/PHASE7_PLAN.md` D1–D16)

110. **LAN in the browser first; the internet later** (owner). Players on the host's network open its address; nothing is installed. TLS, per-IP limits and a browser datagram transport are future "option B" (`PHASES.md` Phase 7).
111. **WebSocket stays the browser transport** (owner: least change). On a LAN loss is close to zero, so TCP's head-of-line blocking costs nothing measurable; unreliable datagrams (WebRTC DataChannel / WebTransport) pay off on the lossy internet and would be one more server adapter, like UDP in Phase 5.
112. **The game uses the best measured settings, fixed** (owner): Delta snapshots (≈ 1/5 of Full's bytes, 0 % off-path; Full stays inside Delta as its keyframe fallback), prediction + reconciliation + smoothing, 100 ms interpolation, **input redundancy off** (TCP already resends; redundancy would only add bytes — it comes back with a datagram transport), no ghost. The game server enforces Delta (`SYNC_FIXED`).
113. **One code base, two thin shells.** `LandingForm` and `MatchView` are shared; the demo (`ui/App.tsx`) adds the Network Lab, packet strip, inspector, Compare and Presenter, the game (`play/PlayApp.tsx`) adds nothing. A texture, effect, rule or HUD change is made once.
114. **The game bundle carries no demo code, and a build proves it.** NetClient's State and Lockstep code is injected (`net/allModels.ts`), so the game's bundle has neither; the demo's Controls-overlay key groups live in `ui/demoControls.ts`. `npm run build` fails if the game JS contains demo-only text (NETWORK LAB, PRESENTER, …). The JS saving is modest (≈ 70 kB minified): Phaser and React are most of the bundle.
115. **Operator messages are refused on the game server, not just hidden.** Anyone can read and change a browser bundle, so the server (`--game`) answers `dev`, `perturb`, `lab`, spectators and the lab room with `NOT_ALLOWED`, never starts `main` early, and refuses to run at all with `NOBU_DEV=1`. Nothing trusts "the connection comes from localhost": behind the emulator every player looks like 127.0.0.1.
116. **One port for everything in production.** `npm start` serves the built page and the game WebSocket (`/ws`) from 8080 — one address to share, one firewall rule. `npm run dev` serves the page from Vite (5173, LAN-reachable) and forwards `/ws` to the game server, so the client code is the same in both: it connects to `/ws` on the page's own host. `?server=host:port` points it elsewhere (e.g. the standalone emulator).
117. **The static server uses Node built-ins only** (no new runtime dependency): GET/HEAD, paths confined to the build folder, immutable caching for hashed files, brotli/gzip for text compressed once and kept in memory. Images and sounds are already compressed.
118. **Room codes are two short words.** An adjective and an animal (40 × 40 = 1 600 codes, 3–5 letters each, chosen so a code typed without a space splits only one way). Easier to say across a room than random letters; plenty for 32 rooms per server.
119. **A private room waits for its host; a quick match doesn't wait.** Friends gather at their own pace, so the host decides (START). The public quick match first waited 10 s for more humans; the owner removed that the same day (R1): late join already lets a slow joiner in, so waiting only delayed everyone. The host passes to the longest-connected human; an empty room lives 60 s so a page reload doesn't lose it.
120. **Masters stay editable; served files are generated.** `assets/` keeps the originals (WAV sounds, PNG art); `npm run assets` writes WebP / OGG tiers into the git-ignored `assets-build/`, which every edition serves. Re-running only rebuilds changed files (state in `node_modules/.cache`, never in the served folder). Budgets fail the build: no served file above 300 kB, `stone_beige` ≤ 160 kB (it is 141 kB, from 2.2 MB).
121. **The player atlas is re-packed per tier, frame by frame.** Shrinking the whole 2048×1024 atlas would leave 0.5 px of padding at a quarter size and frames would bleed into each other; each frame is cut, resized and packed with fresh 2 px padding instead. Pivots are fractions of a frame, so they carry over.
122. **Tier swaps restart the scene.** Phaser animations hold references to their textures, so swapping textures under a running scene is fragile. The scene restarts (≈ one frame; the NetClient and the match go on), and in its `init` — when no object uses the old textures — the new ones replace them and the animations are rebuilt. The scene always starts on Low, so the first frame comes fast.
123. **Raw player frames are not served.** The 7.6 MB of `sprites/player/**` only feed `npm run pack-assets`; they moved to `assets-src/player/` and no edition serves them (the demo used to, as part of Vite's public folder).
124. **Latin font subsets only.** `@fontsource` packages ship Latin-ext, Vietnamese and Devanagari files too; the UI uses only Latin (other characters fall back to a system font). Fonts in the build: ≈ 3 MB → 328 kB (142 kB of woff2 that browsers load).
125. **Smoke stays on this machine.** Its game-edition steps bind 127.0.0.1 (port 8090), as every test does (Phase 5 D15); the LAN path was checked by hand from this laptop's LAN address, and a second machine is the owner's check.

### Phase 7 owner revision: room options and touch devices (2026-10-12, `docs/PHASE7_PLAN.md` §9, R1–R9)

126. **Room options belong to the host and the lobby** (owner). One person shapes a private match, before it starts; mid-match changes (a map switch, a cap below the players present) would be confusing or impossible. The server takes the complete set each time (validated as a whole), so no partial or contradictory state exists.
127. **No bots by default in private rooms** (owner): a room is for the people who joined. *Fill empty slots* is an option; then bots fill to max players and make way for a human who joins. A room needs at least 2 participants to start, counting the bots it would add.
128. **What the host picks shows in the lobby's arena.** The room switches to the next map, puts everyone on spawn points (they can't move before GO), adds the bots, places **preview power-ups** where they could appear and gives everyone the always-on effects (rifle sprite, speed ring, shield bubble). Players see the choice instead of reading about it.
129. **Always-on power-ups are permanent timers in the shared combat state (−1).** The server and the client's prediction step the same `stepCombat`, and the client adopts the server's combat state, so prediction agrees without the client knowing the room's options. A permanent weapon reloads forever; pickups never replace or shorten a permanent power-up; an always-on power-up never spawns, and an always-on weapon stops both weapon pickups.
130. **Always-on Shield = every life starts shielded** (owner). A shield that never breaks would make everyone unkillable; one per life keeps the match a match.
131. **Rooms return to their lobby after each match**, so the host can change the options; a quick match keeps cycling by itself.
132. **The touch UI is decided once per page from the pointer type** (`(pointer: coarse)` with touch points), not the screen size: a small desktop window keeps the keyboard UI, a tablet with a keyboard case still gets touch controls. `?touch=1` / `?touch=0` force it (testing, odd devices).
133. **The joystick produces ordinary key bitmasks** (8 directions, a dead zone of a quarter of its radius). Nothing downstream changes: the same inputs, prediction and server rules as WASD. Its touches go to its own element, so the arena's touch (aim + fire, as before — owner) works at the same time.
134. **Portrait keeps the 16:9 arena** at full width on top and uses the rest of the screen for the controls (owner). A portrait arena would change the game (every map is 1280 × 720); rotating the view would make aiming unnatural.
135. **Only critical actions get thumb buttons** (move, aim / fire, dash when available, reload); everything else lives in the menu (settings, mute, leave; the demo's Lab, inspector and Presenter bar). Compare and the Presenter remain desktop tools.
136. **The static server re-checks a file before serving its cached compressed copy** (size + mtime). Found in the revision: rebuilding while `npm start` runs served the old page.
137. **Floating sticks replace the fixed joystick and touch-to-aim** (second touch revision, 2026-10-29). The left half of the screen moves, the right half aims; the stick appears where the finger lands. The move stick still produces 8-direction key bitmasks (#133), because the server only knows keys. The aim stick sets the aim angle over 360° and holds `fireDown` past a dead zone of a quarter of its radius (`aimStick` in `game/input.ts`). Touching the arena no longer aims (the scene skips its pointer handlers in the touch UI, except in Compare, whose InputDriver owns the pointer).
138. **A forwarded port reaches the server from 127.0.0.1, so remote visitors are told apart by the `Host` header** (`shared/src/net/localHost.ts`), not by IP. Local Host = the demo server; any other Host on 8080 = a second, game-mode `GameServer` in the same process (Delta only, no lab / operator messages, its own rooms, so a tablet never meets the demo's lab). 5173 (a Vite plugin) and 9001 (`ControlServer.hostAllowed`, when bound to loopback) answer other Hosts with a 403 "Restricted" page; the emulator's WebSocket also refuses them. The header is client-supplied: this stops accidents on a trusted network, not an attacker, which matches the project's LAN-only scope (Option B, internet play, would need real auth).
139. **The demo builds `dist/game` once** (`scripts/demo.mjs`, only when `index.html` is missing) so 8080 has a page to serve. After client changes run `npm run build` to refresh what remote players get. `npm run dev` sets Vite's `allowedHosts: true` for the game on 5173; its 8080 answers HTTP with a pointer to the game page.
